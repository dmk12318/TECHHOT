## 2026-10-09 成本上限：只出模型费

- 原因：上一条「成本上限：只出模型费」的约束下，B 是唯一不用绑卡、不用常驻服务的路。
- 影响：
  - 站点变成「每天一张快照」：没有后台、没有实时热度、没有公开 API 与 MCP、没有反馈表单。

（被放弃的路线 A：Oracle Cloud Always Free（Arm Ampere A1）跑完整 Docker Compose，功能全，

- 背景：科技只是第一个板块，将来要和别的领域并成综合站。类别的 key 上线后不能改，
  所以现在怎么分，直接决定将来合并要不要返工。
- 选项：类别按内容形态分（引擎示例的做法）／按领域分；板块单独占一个类别／只用 `section` 和 key 前缀表达。

  **板块只用 `section` 和 key 前缀表达**（科技类别的 `section` 全写「科技」，key 带 `tech-` 前缀）。
  取消「互联网平台」类，AI 单独成类，新能源与汽车合并，类别名一律书面语。

  - 已知代价：筛选栏是扁平的一行，合并后会变成二三十个标签，到那天再定忍／写模块做两级筛选／改粒度。

## 2026-10-09 选稿门槛按 Gold 校准下调：60/65/76 → 48/50/52

- 背景：引擎自带门槛是 AIHOT 在 AI 行业、面向 AI 重度读者校准的。换成「公职读者 + 门户科技」后，
  实跑 14 条源、100 篇文章，59 篇判过分里**过 76 的一条都没有**，最高 71——T2 媒体稿一条都进不来。
- 做法：从已采集的资料里取 90 条人工标注（9 该选／6 两可／75 不该选），跑两轮评测。
- 发现：光调门槛没用。"该选"的分数在 40–62，"不该选"的在 55–66，**两个区间几乎完全重合**，
  降门槛只是在拿查准率换查全率。真正的修法是改评分标准。
- 决定：先改标准，再动门槛。标准里把「厂商自报运营数据」「单款车型上市」「会议活动与招标本身」
  「工具类小更新」「对既有事件的回应与表态」明确压下去；门槛改成 **T1 48 / T1_5 50 / T2 52**，
  `understandFloor` 50 → 44。
- 效果（同一批 90 条样本，标注经用户复核后重算）：F1 从 0.583 升到 **0.842**，
  查准 0.727、**查全 1.0**（8 条该选的全部选中），剩下 3 条多选是双方都认定属于边界的条目。
- 影响：门槛附近的资料变多，用「精选写法」的内容随之增加，模型费会略涨。
  样本只有 90 条、标注是第一遍，样本攒多了要重跑校准（做法见 `engine/docs/selection.md`）。

## 2026-10-10 不配 Jina Reader，接受"部分文章只按摘要判断"

- 背景：引擎在直连取不到正文时，会自动回落到 Jina Reader 补正文；它是按请求计费的付费服务。
  实测（181 篇）里取不到正文的是 6 篇（The Verge 4 篇、欧盟数字政策 2 篇），**是逐篇失败、不是整源失败**。
- 选项：买 Jina 的 key；接受这部分文章按摘要判断。
- 决定：**不配 key**，接受质量损失。
- 原因：符合「只出模型费」的成本口径；而且影响面很小（6/181 ≈ 3%）。
- 影响：
  - 这类文章引擎会重试三次正文提取、之后标成 `unconfirmed` 并按订阅摘要判断，标题摘要照常出。
  - 一次性管线（`scripts/run-once.ts`）不等这些重试：带 `processing_retry_at` 的条目留给下一次运行。
  - **不要用 `summaryIsBody: true` 绕**：那会让整个源都放弃抓原文页，把现在能抓到的正文一起丢掉，
    为了省 3% 的噪声换来大部分正文损失，不划算。

## 2026-10-10 综合站（DAILY HOT）做成导航页，不做跨板块去重

- 背景：讨论「多板块缝合」的形态。原方案（`docs/规范/类别方案.md`，时名《类别方案与缝合规则》）
  是把多个领域并进
  **一个**引擎实例，用 `section` 分节 + `tech-`/`fin-` key 前缀来避免将来返工。讨论中一度改成
  「六个板块各自独立运行 + 门户跨板块去重聚簇、另出一份综合日报」，后否掉。
- 选项：
  1. 一个实例内缝多板块（原方案）；
  2. 六站独立运行 + 门户做跨板块去重聚簇、出综合日报（门户＝第 7 个引擎实例，
     用 `POST /api/ingest/items` 把六站条目灌进来）；
  3. 六站独立运行 + 门户只做导航页，每块列本期最热五条，**不去重**。
- 决定：走第 3 条。门户是导航页 + 六块各五条，六个板块独立运行、独立出刊、独立订阅。
- 原因：
  - 第 2 条要去重，就得把六站条目灌进门户。而引擎的热度按「每个独立媒体算一次」算，
    按板块整体推过去会让热度全部塌成 1 家，必须按原始媒体拆约 300 个外部信源；再加上要等六站
    跑完的中心调度、门户自己多跑一轮模型的费用——为了消掉「首页出现两条同一件事」这点观感问题，
    代价不成比例。
  - **重复的代价有界**：门户首页 30 条里顶多两三条看着像两件事，读者顶多觉得「这条刚看过」。
  - 跨板块重复恰恰最容易发生在最热的事上（芯片出口管制、AI 公司融资、车企财报），因为财经媒体
    本来就在报科技的事——**理由要说「不要紧」，不要说「不会发生」**。
  - 单站失败只影响门户上对应那一块，不连带崩；门户自己不跑引擎、不调模型。
- 影响：
  - 门户＝静态页 + 六份小 JSON。不引入第 7 个实例、不引入中心调度、没有额外模型费。
  - 各站导出的 JSON 必须带：板块名、标题、链接、来源、热度、**数据截至时刻**。
    少了最后一项，门户就守不住「不假装最新」这条口径。
  - 门户**不显示可横向比较的热度数字**（六站基数不同，不可比）；时效措辞写「各板块数据截至
    各自本期出刊时刻」，不写「截至现在」。
  - 放弃的东西：跨板块的主编视角与综合日报。第六份《跨板块缝合规范》不写。
  - **加板块的方式随之改变**：不再往同一个实例里追加 key，而是另起一个独立站
    （新仓库 + 新库 + 新源清单 + 新一轮门槛校准）。
  - `docs/规范/类别方案.md` 里「合并后筛选栏变长」那条代价不再存在；
    但那份文件里 key 前缀、`section` 写法等规则对**单站内部**仍然有效（既有 key 已上线，不再改）。

## 2026-10-10 静态站的「全部动态」和搜索改成浏览器本地算

- 背景：第一次拿真浏览器量静态产物（`apps/web/tests/static-nav.test.ts`）时发现，静态站并不只是
  「慢一拍」，而是坏了好几处：
  1. 「全部动态」列表里 40 条有 38 条点进去 404 —— 列表来自运行时查询（`/api/site/pool`），
     而导出的页面只有 sitemap 里那几十条精选；
  2. 类别筛选、翻页、搜索排序全是**静默失效**：静态托管对 `/all?category=…`、`/all?page=2`
     一律回同一个 `/all` 的 HTML 和 `all.data`，页面照旧显示第一页，读者看不出哪里不对；
  3. 桌面搜索框提交后同样只是回到没筛过的列表。
  原因是引擎的页面都是服务端查数据的，只有「没有查询串的那一页」是能预渲染的。
- 选项：
  1. 只导出「精选集合」，静态站的列表也只列精选（每条都有页面，改动最小）；
  2. 列表与搜索整体搬到浏览器：导出时生成一份全量数据（`pool.json`），前端做筛选/翻页/搜索；
  3. 接受现状，静态站只当快照看。
- 决定：走第 2 条，同时把「全部动态」里的每一条都预渲染出页面（498 页）。
- 原因：
  - 第 1 条等于把「全部动态」变成「精选」的副本，还要把本地搜索限制在几十条上，
    「搜站内内容」这个需求就落空了；第 3 条是发一个点进去就 404 的站，不如不发。
  - 第 2 条的代价可控：`pool.json` 现在 258 条 119 KB，接口自己封顶 2000 条（约 1 MB，Pages 会 gzip）。
  - 预渲染条目页是必须的：列表链到哪一条，哪一条就得有页面。
- 影响：
  - 静态站的筛选、翻页、搜索是**简版**：只搜标题与摘要（不搜正文）、相关度按标题/摘要算、
    「一手」按导出的 T1 信源名单筛。服务端那套（trigram 正文搜索、按 T1/T2 分档）只有跑着 api 的站才有。
  - `export-static.ts` 现在会查一次库拿 T1 信源名单；`pool.json` 只随导出走，不进仓库。
  - 条目越攒越多 → 预渲染页数和分享图都会涨：分享图已改成「抓过的存 `.data/og` + CI 缓存」，
    只补新出现的；预渲染页数受接口 2000 条上限约束（约 2200 页，一轮十几分钟）。

## 2026-10-10 删掉引擎自带的「Agent 接入」页，静态站发到 GitHub Pages 的项目站

- 背景：静态站上没有任何后端，而「Agent 接入」页讲的是公开 API 与 MCP（侧栏、手机「我的」页、
  条款页脚都链过去），读者点进去只会看到取不到的地址；另外 Pages 的项目站是**子路径**
  （`dmk12318.github.io/TECHHOT/`），而产物里原本全是根路径地址，直接发上去整站没样式没脚本。
- 选项：
  1. 保留 Agent 页，只把它铺成静态文件（前一版就是这么做的）——页面还是空头承诺；
  2. 删掉 Agent 页；发布上，把仓库改名成 `dmk12318.github.io` 走根路径，或者给构建加子路径前缀。
- 决定：**删掉 Agent 页**；发布**保留仓库名 TECHHOT，给构建加 `/TECHHOT` 前缀**（用户拍板）。
- 原因：静态站永远不会有 api，留着一个讲接口的页面不如不留；改仓库名会让仓库名与站名割裂，
  而子路径前缀是一次性配置（`SITE_URL` 里带不带子路径决定前缀），以后换自定义域名只改一个变量。
- 影响：
  - 删掉的文件：`apps/web/app/routes/agent.tsx`、`apps/web/app/features/agent/`（4 个）、
    `apps/web/tests/report-discovery.test.ts`（整份都在测那一页），以及 routes.ts 的路由、
    侧栏与「更多」页的入口、条款页脚链接、smoke 清单里的 `/agent`、
    sitemap 里的 `/agent` 条目、导出里的 `/api/v1/agent`。
    **这是改引擎本体**：以后合上游更新时，这几处会冲突（要么保留删除，要么把页面找回来）。
  - 前缀的规则：`vite.config.ts` 的 `base` 和 `react-router.config.ts` 的 `basename` **必须逐字相同**
    （都带结尾斜杠），两处都从 `SITE_URL` 的路径里取。React Router 预渲染是拿 basename 拼
    `${basename}${path}.data` 请求的，跟 `base` 不一致会一路 404（这个坑踩了两次）。
  - React Router 会把预渲染出来的页面写进 `build/client/TECHHOT/…` 多一层，而静态托管是把产物
    根目录当站点根目录的，所以导出时把那一层提上来（`export-static.ts` 里那一段）。
  - 写死在 HTML 里的地址（图标、manifest、RSS、本地数据文件）走 `app/lib/base-path.ts` 的
    `sitePath()` 加前缀；路由链接由 router 自己加，不用管。
  - `robots.txt` 与 `manifest.webmanifest` 以前是**没渲染的模板**（`{{siteName}}`、`{{siteUrl}}`
    原样发出去了），现在改成从 api 取渲染好的，manifest 里的地址再补上前缀。
  - 产物根目录放一个 `.nojekyll`：Pages 默认按 Jekyll 处理，会把 `_.data` 这类下划线开头的文件丢掉。
  - 发布走 `actions/configure-pages`（带 `enablement: true`，仓库没开过 Pages 时顺手开）+ upload/deploy；
    出刊那条与新增的「发布」那条都会发，共用同一个 Pages 环境。
