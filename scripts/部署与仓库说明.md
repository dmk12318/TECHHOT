# 部署与仓库说明

路线 B（GitHub Actions 定时跑 + 免费 Postgres + 静态页）的仓库怎么组织、上线要配什么。

> 第一次配仓库，照着 [GitHub 仓库配置教程](GitHub仓库配置教程.md) 一步步做；
> 这份文件是参考手册，讲“为什么”和“注意什么”。

## 仓库结构

| 位置 | 是什么 |
| --- | --- |
| 根目录 | 项目规则与文档：`AGENTS.md`、`README.md`、`docs/`、`records/`、`scripts/`、`.github/workflows/` |
| `engine/` | AIHOT 引擎，**含我们的改动**（行业配置、站点身份、提示词、`scripts/run-once.ts` 等） |
| `.upstream/engine.git` | 引擎上游的 git 历史，**只在本地**（`.gitignore` 里），用来跟上游对比和拉更新 |

### 为什么引擎是"直接放进仓库"而不是 submodule

我们对引擎的改动很多（`industry/` 的类别、信源、提示词，`site/` 的站名与品牌，还有新加的脚本）。
submodule 只能指向一个外部仓库，装不下这些改动；真要用 submodule 就得先 fork 一份上游，
而 fork 的目录布局（引擎文件在仓库根）跟本项目的布局（引擎在 `engine/` 子目录）对不上。
所以把引擎的文件直接放进仓库，同时把上游的 `.git` 挪到 `.upstream/engine.git` 保留历史。

**跟上游对比或拉更新**：不用切目录，显式指定 git 目录和工作区就行。

```powershell
$gd = 'D:\File\Codex\DAILY HOT\.upstream\engine.git'
$wt = 'D:\File\Codex\DAILY HOT\engine'
git --git-dir=$gd --work-tree=$wt log --oneline -5          # 看当前对应上游哪个版本
git --git-dir=$gd --work-tree=$wt fetch origin             # 拉上游最新
git --git-dir=$gd --work-tree=$wt diff origin/main --stat   # 看上游改了什么
```

## 建 GitHub 仓库

**必须建成 public**：免费版 GitHub Pages 只对公开仓库开放，公开仓库的 Actions 分钟数也不计费。
代价是仓库内容（包括我们改过的引擎和提示词）谁都看得到——这不影响运营，因为密钥一律走 Secrets，
`.env` 在 `.gitignore` 里。

建的时候**不要**勾选 "Add a README / .gitignore / license"，否则第一次推送要先合并。

建完在本地接上并推送：

```powershell
cd 'D:\File\Codex\DAILY HOT'
git remote add origin https://github.com/<你的用户名>/<仓库名>.git
git push -u origin main
```

推送时 Git Credential Manager 可能弹一次浏览器让你登录 GitHub，登录一次以后就记住了。

## 要配的仓库设置

**Settings → Secrets and variables → Actions**：

| 类型 | 名字 | 内容 | 必需 |
| --- | --- | --- | --- |
| Secret | `DATABASE_URL` | Neon 的 direct 连接串（`sslmode=require`，**不要** `-pooler`） | 是 |
| Secret | `LLM_API_KEY` | 模型接口的 key | 是 |
| Secret | ~~`TEST_DATABASE_URL`~~ | **不再需要**：CI 的测试用 runner 自带的 PostgreSQL 容器（见下），不碰 Neon | — |
| Variable | `SITE_URL` | 站点对外地址（有域名后填，生成链接用） | 否 |
| Variable | `LLM_BASE_URL` / `LLM_MODEL` | 换模型时填，不填用 DeepSeek 的默认值 | 否 |

## 两个 workflow

| 文件 | 什么时候跑 | 干什么 |
| --- | --- | --- |
| `.github/workflows/daily.yml` | 北京时间 08:10 和 20:10（GitHub 的 cron 用 UTC，所以写 `10 0` 和 `10 12`） | 跑 `engine/scripts/run-once.ts`：采集 → 处理/评分/写作 → 归组 → 出刊 |
| `.github/workflows/ci.yml` | 每次推送、每个 PR、手动 | `typecheck` + 不需要数据库的测试 + Web 测试 + 后端全套测试。**测试库里用的是 runner 自带的 PostgreSQL 容器**，不是 Neon |

测试为什么不用 Neon：测试框架会给每个测试文件**复制一份"模板库"**（`CREATE DATABASE … TEMPLATE`），
而 Postgres 要求复制时模板库上没有别的连接。Neon 的计算节点内部进程会挂在每个库上，
复制会间歇性失败（`source database "dailyhot_ci" is being accessed by other users`）。
引擎上游自己的 CI 也是在 runner 里起一个 Postgres 容器。**Neon 只给 `daily.yml` 用**（那是真实数据）。

两次运行不会重叠（`concurrency: pipeline`）——同一个库上并发跑会互相抢队列。

## 几个要知道的行为

- **出刊失败会让 workflow 失败**，GitHub 会发邮件给你。这是当前唯一的告警渠道
  （原版引擎靠常驻 worker 发飞书，路线 B 没有常驻进程）。"这一期的窗口里没有任何资料经过评判"
  也算失败——引擎故意不把"采集失败"伪装成"平静的一天"。
- **仓库 60 天没有任何活动，GitHub 会自动停用定时任务**，并给你发邮件。到时候点一下恢复即可。
- **阶段 3 还没做**：静态页导出与发布。`daily.yml` 最后留了 TODO，那一步接上之后，
  这个 workflow 才会真正产出对外的网站；现在它只跑到"出刊"，结果落在数据库里。
- 日志在 Actions 的运行页里；`run-once.ts` 每轮都打一行 JSON，能看到"还有多少活没干完"。
