## 阶段 2：把常驻服务改成「跑一次就跑完」（路线 B 的核心工程量）

- [x] **写驱动脚本**：`engine/scripts/run-once.ts`。引擎的 worker 是常驻调度器（每分钟抓取、每五分钟扫处理），
  没有"干完就退"的入口；这个脚本把 worker 注册的那套任务处理器装上，再把它的定时任务在一个循环里反复调用，
  直到没有待处理的活，然后出刊、退出。**业务逻辑一行没改，调的都是引擎自己的函数。**
  - 用法：`node --env-file=.env scripts/run-once.ts [--sources id,id] [--no-collect] [--budget 45] [--report-anyway]`
  - 退出码：0 = 干完了（含"这天没有大事，所以没出刊"）；1 = 超时还有活；2 = 出刊失败。
  - 实测（2026-10-10 凌晨）：两条源 → 抓到 6 篇新文章 → 判完 → 归组（事件 126 → 128）→ 出刊，
    5 分钟跑完，`timedOut: false`，退出码 2（出刊失败，原因见下）。
  - 踩坑：**pg-boss 的定时排程存在数据库里**。常驻 worker 注册过的 `cron.*` 队列，一次性脚本没有对应处理器，
    会一直按点生成任务、越堆越多，"队列空了"永远不成立。脚本开跑前先删掉这些队列（连带排程和残留任务），
    已修复并复测。
  - 已知：**每次运行会重试"出刊"直到成功**。现在退出码一直是 2，因为最后到点的那期日报（10-09）的窗口
    （10-08 08:00 → 10-09 08:00）里没有资料——引擎故意把它当失败报警，不伪装成"平静的一天"。
    **10-10 08:00 之后那一期有内容，就会正常出刊。**
